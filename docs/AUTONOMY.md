# Personal action policy and audit

Live workspaces default to `APPROVAL_POLICY=money`: Gmail send/reply and Calendar create/update/delete execute through ActionService without a separate review. `APPROVAL_POLICY=all` retains native review for supported native, browser and connector writes. Samples retain their scripted reviews. Missing Gmail capabilities (such as label-management APIs) are not invented by this change; optional browser/MCP connectors can provide additional operations.

Payments, purchases and money transfers always require a native review. The model cannot approve an action. The phone's browser card opens its review in Activity, where you can inspect the tool, site and control, open the page to check the amount/recipient, approve or decline. Watching does not grant control; taking control invalidates the pending browser reference, so prepare a fresh review after handback.

Browser reviews bind the exact owner/session, snapshot, document and target frame, element, action, page text and form state. Effective form action/method/target and submitter overrides, including form-associated controls outside the form, are included. Password/masked values participate only in a private digest; they remain absent from snapshots, review data and audit. Approval uses a separate HMAC-authenticated server-to-worker endpoint; `browser_act` rejects approval/bypass arguments. The worker serializes validation/dispatch and persists a one-use receipt before executing. Changed amounts, payees, iframe text, form destinations, navigation, takeover, closed sessions or worker restart reject old references. Known completed receipts return without clicking again. Uncertain execution is not retried automatically.

Gmail/Calendar use the same atomic claim, account binding, cancellation/expiry checks, target-version checks and uncertain-write handling in both policies. Native automatic POST `/api/actions` requests require a unique 16–160 character `idempotencyKey` body field (or `Idempotency-Key` header). Reuse it after a lost response; changing the input under the same key is rejected. The native email/event editor retains its key while that editor is open. Closing/reopening an editor starts a new intent: check Activity/provider before resubmitting an uncertain action. Do not use a new key merely to retry an uncertain request.

Activity → Action log shows owner-scoped, paginated time, tool, target, summary, actor and result. `external_action_log` is a distinct SQL table with INSERT-only application access and triggers rejecting UPDATE, DELETE and TRUNCATE. Start records are saved before external dispatch; an audit-start failure blocks dispatch. Later rows describe success, failure, refusal or unknown outcome, without changing earlier rows. The DB administrator can change the schema; this is not a tamper-proof ledger.

Native actions, browser calls and human console inputs, computer commands/files/media and configured image generation use shared audit boundaries. Full commands, stdout/stderr, file bytes, email bodies, filled values, cookies, authorization headers, private binding data and query strings are excluded. Backend receipts hold normal execution evidence; the audit uses safe summaries and outcome categories. Terminal append failures do not turn a confirmed external operation into a retryable failure. A safe terminal completion journal retains known results when their append fails. Startup and the task worker's minute maintenance recover known native/computer/image terminal results from persisted receipts; other interrupted boundaries receive an unknown marker on startup. Background computer results are reconciled by maintenance or when their status is polled. Enable `TASK_WORKER_ENABLED=true` for autonomous background reconciliation.

The additive interfaces for connectors are `ActionService.registerExternal(tool, executor)`, `proposeExternal(owner, trustedIntent, key, taskId?)`, and `ActionLog.run`. Only server adapters may classify money, produce safe summaries and register execution bindings. Public `/api/actions` accepts the existing Google schemas, never arbitrary connector bindings. Connector implementations must bind their config/allowlist/tool/arguments and revalidate those before dispatch.

## Limits

Financial detection covers recognized browser controls and associated submission context in English, Portuguese and German. It is a heuristic: arbitrary or malicious site handlers can perform financial actions behind unrelated labels. Inspect unfamiliar transaction pages and use Take control when appropriate.

An open networked shell can perform HTTP/SMTP/API operations inside arbitrary programs. Command invocation/outcome is logged; individual HTTP effects and their financial semantics cannot be reliably classified. Money review applies at explicit native/browser/connector boundaries, not to every possible program inside the shell. The computer receives no app/provider credentials; do not copy account/payment secrets into it. `all` does not add native reviews to arbitrary computer command contents.

Cancellation/takeover before dispatch prevents execution; an already dispatched external effect cannot be undone. Lost responses, interruption, or missing receipts may leave `outcome_unknown`. Check the provider/site/workspace before preparing a fresh action. Live Google accounts, physical phones and Docker remain separate deployment checks; automated tests use synthetic account/provider fixtures and real Chromium with local page fixtures.
